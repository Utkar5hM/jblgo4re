# Go 4 reverse engineering notes

These findings are from `Go4_ota_all0600.bin`, the official `Go4_ota_all0640.bin` image, and a live Go 4 on 31 October 2026. A read-only BLE query confirmed the unit runs 0.6.4.0; this matches the analyzed release, though a cryptographic equality check against the installed bytes is unavailable. Addresses below refer to raw partition load addresses, not offsets in the OTA container. Unless marked 0.6.4.0, addresses refer to the older 0600 image.

## Local toolchain

Ghidra 12.2 and Temurin JDK 25 are installed under ignored `.toolchain/`. The source OTA, extracted partitions, Ghidra projects, and raw USB descriptors are under ignored `captures/`.

```bash
python3 tools/extract_fw.py captures/Go4_ota_all0600.bin
JAVA_HOME="$PWD/.toolchain/jdk" .toolchain/ghidra_12.2_PUBLIC/ghidraRun
```

The analyzed projects are `captures/ghidra/go4_stage0_v3` and `captures/ghidra/go4_main_v3`. Load `stage0_40000.bin` as `ARM:LE:32:Cortex` at `0x40000` and `main_00000.bin` as the same processor at `0x0`. The Ghidra scripts in `tools/ghidra/` seed Cortex-M vector handlers, find literal references and immediates, and dump decompiled functions.

The newer 0.6.4.0 image is saved as `captures/Go4_ota_all0640.bin` (SHA-256 `56867f41fb985776ae530b5a7d50ae01bd188561480caf0aae66661c3dc8d3aa`). It matches the byte stream at the [official Harman OTA URL](https://storage.harman.com/release/portable/go4/Go4_ota_all0640.bin), and its [OTA manifest](https://github.com/vddCore/jbl-firmware-archive/blob/master/Firmware/speaker/JBL%20GO%204/20e4/release/go4_ota.json) identifies version 0.6.4.0 and target PID `20e4`. Its extracted files and analyzed Ghidra projects are under `captures/firmware0640/`, `captures/ghidra/go4_stage0_0640`, and `captures/ghidra/go4_main_0640`. All four partitions have the same sizes as 0600 but different content. The official 0.7.4.1 image has not been acquired.

## Live BLE control probe

The Go 4 advertises JBL service data `FDDF` and Harman manufacturer ID `0x0057` with product ID `0x20e4`. Its BLE control service is `65786365-6c70-6f69-6e74-2e636f6d0000`, with notify characteristic ending `0001` and write characteristic ending `0002`. A read-only request `aa 41 00` returned command `0x42`, payload `00 06 04 00`, and a trailing zero byte: firmware **0.6.4.0**. Request `aa 11 00` returned device-info tokens including `0x42=20e4`, `0x44=e4` (100%, charging), and `0x4d=30363430` (ASCII `0640`). The read-only `tools/ble_probe.py` reproduces this and suppresses identity fields.

The observed frame shape and opcodes agree with [JBLControl's source](https://github.com/ffrafat/JBLControl/blob/main/Sources/JBLControlKit/JBLProtocol.swift) and [OpenJBL's APK-derived protocol notes](https://github.com/NiceDayZc/openjbl/blob/main/docs/PROTOCOL.md). Both source trees are cloned only under ignored `captures/vendor/`. [ConnectPlus](https://github.com/pembem22/connect-plus) implements older JBL BLE control and a DFU flow, but its own README limits flashing validation to CSR speakers. It is not a verified updater for this Go 4's Vimicro/Zgmicro image. No BLE firmware write, reset, or mode command was sent.

## OTA layout

Container SHA-256: `2f440402006a65d29778075021e58cb174cf20626920187acfe0faaee75a5d19`. The file begins with `HMHEADER9`, has four `PARTHMDT` partitions, and ends with `FOOTERHM`.

The byte at header offset `0x10` is the partition count (`4`). Four 13-byte descriptors follow at `0x11`; each parses as a one-byte partition ID and three little-endian 32-bit fields: length, a still-unknown parameter, and a **custom CRC-32** of the partition payload. IDs are `1, 2, 3, 6`. Stage-0 function `0x43d4e` initializes the CRC to `0xffffffff`, feeds data through table function `0x44568`, and complements the result. The table at `0x5dc14` is a reflected CRC with polynomial `0x681bb522`. All four descriptor values match the computed CRC in both 0600 and 0.6.4.0, including the identical CRCs of three substantially different partitions. Standard zlib CRC-32 uses another polynomial and therefore does not match. `tools/extract_fw.py` now validates all four CRCs as well as markers and footer.

`tools/repack_fw.py` replaces one partition with data of the same length, updates its CRC in the header, and verifies the resulting container. Replacing stage 0 with identical bytes reproduced the official 0.6.4.0 OTA byte for byte (SHA-256 `56867f41...`); a one-byte test edit generated a new CRC and passed offline extraction. These checks establish the outer container format only. The device's board checks, flash mapping, boot behavior, and recovery path remain to be verified before a modified image is sent.

### OTA receive path in 0.6.4.0

The same BLE command dispatcher that answered the live version query handles OTA-related opcodes. In stage 0, `0x57dcc` routes `0x43` to transfer setup `0x519f8` and `0x44` to a queued data path; `0x47`, `0x48`, `0x4a`, `0x4d`, and `0x4e` handle additional control/status operations. The setup path requires a 12-byte payload and checks the device mode through `0x4f4d2` before starting. Queued chunks reach `0x59494`, which checks sequence numbers and passes bytes to container parser `0x52dc4`. That parser recognizes `HMHEADER`, `PARTHMDT`, and `FOOTERHM`, and calls flash callback `0x5bc24`. The callback writes through `0x52460`/`0x53b50`; completion uses `0x41470` to compare a custom CRC of the written flash contents with the descriptor value. This is a static map, not a validated host-side update sequence. No update command was sent to the live speaker.

The first two reset handlers disassemble as Thumb code. The `0x400000` references from partition 1 appear to point to a separate ROM or address space; this mapping remains unverified. Do not concatenate the executable partitions into one address space without resolving that overlap.

## Live USB service mode

The Linux host enumerated `0ac8:bb91`, manufacturer `Zgmicro`, product `JBL Go 4`, `bcdDevice 0.01`. Bluetooth disconnected. The device exposes:

- USB Audio Class 1.0, 48 kHz, 16-bit, stereo playback on isochronous OUT endpoint `0x02`.
- Audio Feature Unit 2: master mute and left/right volume controls. ALSA reports the volume control as `0..100` with `0.00..0.39 dB`, effectively no attenuation. PipeWire can still apply host-side software volume.
- CDC ACM control/data interfaces with bulk OUT `0x04` and IN `0x83`. There is no HID interface, so no standard USB button events. The CDC control interface has no notification endpoint and Linux did not create `/dev/ttyACM*`; passive captures yielded no data, and read-only version queries got no reply.

The device node was `/dev/bus/usb/003/096` for this capture and is root owned. That path will change after re-enumeration. A temporary per-user ACL was granted with a PolicyKit password prompt; it disappears when the device is unplugged.

`tools/cdc_listen.py` is a passive reader for bulk IN `0x83`; it does not transmit. A 30-second capture received no bytes. Whether any speaker buttons were pressed during that window is unconfirmed. A 25-second ALSA poll of the USB PCM volume control showed `0,0` throughout, with button presses likewise unconfirmed.

In a later 40-second synchronized capture, the user pressed Volume+, Volume−, and Play in USB service mode and reported no change in loudness or playback. CDC IN emitted no bytes, the ALSA USB PCM volume control remained `0,0`, and the device stayed enumerated as `0ac8:bb91`. This confirms that these buttons provide no observed control in this mode on the tested unit; it does not yet locate the firmware gate or prove the buttons are electrically disabled.

`tools/cdc_version.py` sends only `AT+HMDevVER\r\n` in a 60-byte frame to bulk OUT `0x04` and reads bulk IN `0x83`. The frame contains a `0f f0` marker, 16-bit payload length, zero-padded payload, and a little-endian CRC-16/CCITT over the first 58 bytes, matching the archived firmware's transmit routine. The live device accepted the 60-byte USB write but returned no data in 2.5 seconds. Repeating the query with CDC DTR set and with the length field set to `0x36` also returned no data; DTR was then cleared. This does not prove that the parser is active in this mode or that the live firmware matches the archived image. No reset, power, or update command was sent.

## Preliminary code paths

- Partition 0 has an `AT+HMDevVER` command and an `AT+HMPowerOff` command in a command parser around `0x4d6d8`. The latter queues message `0x902` with parameter `7`. The transport for these commands is not yet identified; do not send them blindly.
- `PowerOffStatusTimer` is created around `0x5952c` with period `3000` (likely milliseconds). Its callback at `0x576b4` sets a state byte to `2` and posts internal message `0x905`. This establishes a power-status timer, not the cause of the user's shutdown.
- Partition 1 has an event-name table at `0xc2130`. IDs include `0x17` = `VOL_UP`, `0x18` = `VOL_DOWN`, `0x22` = `PLAY`, `0x23` = `PAUSE`, `0x88` = `ENTER_DEMO_MODE`, and `0x2` = `POWEROFF`.
- Main event routing around `0x929fe` forwards the volume and demo-mode events into `0x8e864`. The event name suggests that service USB playback may be tied to a demo mode, but that relationship is not yet proven.
- The event router `0x8e864` sends `0x17` to volume-up handler `0x8fc24` and `0x18` to volume-down handler `0x8f9b8`. Both handlers return early when state byte `+0xf6` equals `2` and a second state test is true. Setters around `0x91fbc` and `0x92030` handle six-byte peer addresses, so this gate is more likely tied to Bluetooth peer state than USB mode. Event `0x88` reaches this router but has no obvious direct handling there, so another handler or a different event path may implement the mode change.
- Partition 0 function `0x40acc` maps six one-bit key masks (`0x01, 0x02, 0x08, 0x10, 0x20, 0x40`) to `AT+HMDevKEY=05,03,02,04,01,00` text and passes them to `0x40a80`. This gives us a key-code map for tracing the button scanner, but the physical button identities are not yet assigned.
- In partition 0, the handler near `0x523e6` receives key message `0x1c00`. For single-key masks `0x02, 0x08, 0x10, 0x20, 0x40` with a zero second word it calls `0x40af4`; `0x4d6fc` can enqueue `0x1c00` through `0x4d6e8` when the key-report gate is enabled.
- The diagnostic key gate is RAM byte `0x200004e8`: parser commands `AT+HMDevKIN` and `AT+HMDevKOF` set it to 1 and 0 respectively. With the gate enabled, `0x4d6fc` queues key message `0x1c00`; the handler near `0x523e6` formats selected masks through `0x40af4` (`AT+HMDevKEY=05/03/02/04/01/00`). `0x40aa8` frames those strings and `0x5a298` sends them on CDC IN endpoint `0x83` when the CDC transport is initialized. This gives a plausible host-side button bridge without adding HID, if the physical key scanner emits those messages during USB audio mode.
- Stage-0 startup calls `0x53ac4`, which runs power initialization `0x57128` and then `0x4cd38`. The latter looks up the `button_dev` driver, registers `0x4d6fc` as a callback, and passes the static button definition at `0x5d200`. Thus the telemetry callback is installed during startup; whether its driver reports events in the live USB-audio state remains unresolved. The second registered callback is a return-only stub at `0x58c24`.
- A timed live capture sent `AT+HMDevKIN`, listened on CDC IN for 60 seconds, then sent `AT+HMDevKOF` to restore the RAM gate. The speaker returned no CDC data. The prior synchronized button capture also had no CDC output while the user pressed Volume+, Volume− and Play, so this telemetry route is not currently a working bridge in service mode. The control scanner or event producer is likely inactive there; the gate itself is not enough.
- On this Linux host, a persistent udev rule now sets the exact `0ac8:bb91` USB device node owner to user `user` with mode `0600`. It removes the per-reenumeration ACL/password prompt for this one device; it grants no general sudo access. Rule: `/etc/udev/rules.d/70-jbl-go4-re.rules`.
- Partition 0 loop at `0x44460` reads exactly 60 bytes through `0x4a744` and passes the bytes starting at offset 4 to the AT parser `0x4d6d8`. Transmit routine `0x4a758` builds 60-byte `0f f0` frames and appends CRC-16/CCITT (polynomial `0x1021`, initial value `0`). Its lower-level function `0x59e2c` submits to endpoint number `0x83`; this matches the live CDC IN endpoint. USB initialization at `0x50a70` sets up the same RAM ring buffer (`0x20003340`) that the parser's read path uses. Together these support a USB command path in the archived firmware, but no response to the live version query has confirmed that path on this unit in service mode.

### 0.6.4.0 cross-check

- The exact live USB device descriptor (`0ac8:bb91`, bcdDevice 0.01) is present in stage-0 at `0x5daac`. Initialization at `0x5aa3c` registers its descriptor table. This places the service-mode USB implementation in the small stage-0 image; the main image may still provide application behavior.
- The first 256 bytes of the USB descriptor block are identical in 0600 and 0.6.4.0, so matching the live VID/PID and USB layout cannot identify the firmware version installed on this unit.
- The 60-byte AT parser loop is at `0x44044` and calls `0x4d71c`; its entry pointer at `0x51b80` sits beside the task name `App USB Transmit`. A callback at `0x51b60` creates that task on internal event `0xa03`. This supports the archived firmware's USB command path, but the live CDC endpoint remains silent.
- Mode-state handler `0x51620` emits event `0x901` when a mode value changes to `2` or `3` from a lower value. Power handler `0x59e32` turns `0x901` into `0x806` when its state byte equals `2`; event router `0x4f7c8` handles `0x806` by calling USB audio setup `0x4fdc4`. That setup registers the USB descriptors and an isochronous audio callback for 48 kHz playback. The physical Play+Bluetooth chord's state-write point is not yet located.
- The mode value used by `0x51620` comes from `0x4f4d2`, which first checks a hardware state through `0x455e4`, then reads fields `+0`, `+9`, and `+0xd` of a RAM object whose pointer is stored at `0x20000070`. This narrows the service-mode entry investigation to writers of that object and its initialization at `0x4251c`; the exact chord handler is still unidentified.
- USB audio callback `0x4c6f0` accumulates incoming PCM and forwards blocks to `0x4feac`, which copies up to `0xc0` bytes to a buffer and signals another task. Neither function visibly applies gain or maps a key event. This is a patch investigation lead, not proof that no later stage can change volume.
- `AT+HMDevKIN` and `AT+HMDevKOF` in parser `0x4d71c` write the same state byte at RAM `0x200004e8` read by key-reporting gate `0x52610` via `0x4d6fc`. The address is present as a literal at `0x4dba4` and `0x52618`; the decompressed RAM image initializes the byte to zero. The two additional functions invoked by those commands (`0x418b6`, `0x419f0`) are stubs in this build. This gate controls diagnostic `AT+HMDevKEY` forwarding; it does **not** establish the cause of the disabled Volume+/Volume−/Play actions.
- Event callback `0x523e8` handles `0x900` by reading the mode byte via `0x5269c`; when it is `1` or `2`, it posts `0xa03`. Callback `0x51b60` handles `0xa03` by creating the `App USB Transmit` task whose entry is `0x44044`. These callbacks occur in the firmware's registration table at `0x5e18c` and `0x5e120`, respectively. The live service-mode CDC endpoint has not replied, so this static path does not establish that the task runs on the tested unit. The same `0x523e8` callback forwards eligible `0x1c00` key events to `0x40af4` for diagnostic reporting.
- `tools/cdc_key_probe.py` was run on the live `0ac8:bb91` unit after granting temporary ACL access to its current USB node. Two bounded captures sent `AT+HMDevKIN`, listened for 20 and 45 seconds, then sent `AT+HMDevKOF`; neither received a CDC IN report. This confirms that the command write completes at the USB host, not that the speaker parser accepts it. No HID interface exists, and the live descriptor has only UAC1 audio plus CDC ACM. Therefore the stock image exposes no host input path for its physical keys in this mode. A custom mode needs a new host-visible control path (most naturally USB HID) and firmware code to emit reports; `KIN/KOF` is not that feature.
- The UAC1 Feature Unit advertises mute and per-channel volume, but ALSA observed a range of `0..100` with only `0.00..0.39 dB` attenuation. The USB PCM callback `0x4c6f0` collects packets and hands buffers to `0x4feac`, which copies at most `0xc0` bytes and raises event bit `0x0c`. These two functions do not perform an EQ or gain operation themselves. The downstream consumer/DSP route has not yet been identified, so the user's report that USB sounds raw is not yet explained by static analysis.
- The USB-audio setup does send commands to the firmware's DSP/IPC command queue: `0x4fdc4` uses command IDs 7, 2, then configures `0x0200` format, 48 kHz, 16-bit and `0xc0` byte blocks; shutdown uses command IDs 3 and 8. Per-block PCM submission in `0x4feac` then copies samples into the shared audio buffer and signals event bit `0x0c`; it does not submit another command for each block. This is the clearest current boundary between USB framing and the downstream playback engine. The consumer of event `0x0c` remains unidentified.
- The event chain confirms normal-mode internal event `0x806` starts the same USB-audio setup (`0x59e32` calls `0x4fdc4`), while event `0x902` stops it. The setup's command `2` carries the 12-byte USB format block through the USB client's channel. The actual per-block signal is a scheduler/event-group bit, not a Bluetooth media callback; the host currently has no way to inject the speaker's physical keys into that event path.
- The USB-audio client channel is created by `0x57068` with `FUN_5ba9c(0,0x10)` and stored at RAM `0x2000053c`; USB commands read that channel index from the same USB state object at `0x20000538`. Its event-`0x0d` callback is `0x59bd4`, which updates the object's state byte. The Bluetooth media/control helpers instead read their channel from a separate object at `0x20000524`. USB and Bluetooth therefore use distinct DSP/IPC channels even though some command IDs overlap; routing USB through the Bluetooth channel would be an unproven and potentially incompatible change.
- The USB control dispatcher `0x5a99c` routes standard interface requests to `0x5ac08`; that handler recognizes HID report-descriptor requests (`GET_DESCRIPTOR`, descriptor type `0x22`) and returns a pointer/length from a linked list keyed by interface number (`0x5ac94`). The endpoint descriptor parser `0x5a418` accepts endpoint numbers through 4, while service mode currently uses EP2/3/4, leaving EP1 unused. This makes HID technically compatible with the stack, but the descriptor-list population/registration mechanism and a mode-specific configuration descriptor have not been located. No firmware patch has been built.
- In the main image, startup at `0x76028` creates `App Task DSP` with entry pointer `0x2199` (Thumb entry `0x2198`). That task creates a 0x28-byte message queue, waits on it, then invokes a callback stored in each received message. A separate `App work_msg` task at `0xafbb4` also runs a callback dispatcher. This narrows the audio handoff search to queue/message producers; neither queue has yet been connected to the stage-0 USB PCM buffer or the Bluetooth audio route.
- The DSP task queue handle is stored at RAM `0x200217e0`; the queue-post helper `0xb0ef8` allocates and posts 20-byte callback records to it. Its wrappers are called by profile/control handlers around `0x7d040`, `0x7d2e8`, and `0x7d400`. These messages establish an app-task control/event channel, not a PCM path; the audio sample route remains to be found.
- `power_smart_control` is created at `0x53034` with two 30,000-unit timers, likely milliseconds. Its status function `0x53f04` samples an ADC through `0x4237c`, smooths the sample through `0x57590`, and maps it through threshold logic at `0x57958` into a level `0..6`. That level is stored in RAM state `0x200000e8 + 3` and passed to `0x59328`. When the level is zero on more than seven consecutive calls and another state check `0x59a9c()==2` holds, `0x59328` posts power-off event `0x902` with reason byte `6`. The functions' use of charger-status bits and level thresholds makes a low-battery or voltage-sag shutdown a strong interpretation. It remains unproven for this unit, and the physical threshold values have not been recovered.
- Another path, `0x50d30`, posts event `0x902` with reason `6` if a flag is set, the `0x59a14()` state equals `1`, and event bit `0x200` is absent. It runs in a loop next to `0x50c0c`, which contains charge-bypass control logic. This is a separate power/charging candidate.
- Further tracing in 0.6.4.0 shows bit `0x200` is checked through the stage-0 GPIO status abstraction (`0x49520`) and the same signal gates the charge-bypass worker `0x50c0c`. That worker reads a charging state byte (`0x49bf0`) and enables/disables a GPIO output through `0x47188`; therefore the bit is part of a power/charge path, not an audio activity indicator. Its physical net name/polarity is not established, so it must not be called VBUS or charger-present yet. The mode-1 shutdown in `0x50d30` is still only a candidate for the user's symptom.
- GPIO setup at `0x43764` configures mask `0x200` from a static descriptor at `0x5d35c` (`0x201,0`). The status abstraction reads that configured pin alongside a GPIO peripheral register. This narrows the unresolved question to board-level pin mapping and runtime state, rather than a generic inactivity timer. Static firmware alone cannot prove why the live unit powers off while charging; a runtime trace of the pin, charge-state byte, and reason-6 event is still needed.
- The live unit currently enumerates as `0ac8:bb91`, with configuration 1 exposing UAC1 stereo playback (interface 1, EP2 OUT, 48 kHz/16-bit) and CDC ACM (interfaces 2/3, EP4 OUT and EP3 IN), exactly matching the service-mode descriptor capture. No HID interface exists. A new HID interface could fit the USB stack's generic HID request handling, but would need the device's button scanner to remain active in that mode, plus descriptor registration and space for a report descriptor; those pieces are not proven. A HID-only patch cannot restore the Bluetooth EQ/audio route by itself.
- A read-only BLE scan while this unit was enumerated in USB service mode found no Go 4 advertising under PID `0x20e4`. That means BLE cannot currently act as a parallel button-control bridge in this mode; it does not establish whether the radio is intentionally disabled or simply not advertising during this session.
- Event handler `0x517d8` maps internal `0xa01` to `0x59ee0`, which posts `0x902` with reason `3` if a callback object is present. It maps `0xa00` to `0x51448`, which posts reason `5` after reset-related work. A search for an immediate `0xa01` producer in the 0.6.4.0 main image found none; neither branch is linked to the reported spontaneous shutdown. This leaves the event source, not just its final power-off action, to identify.
- The stage-0 initialized RAM is compressed in the image. Reset helper `0x400ac` expands the stream at `0x5e1a0` to 0x760 bytes at `0x20000000`; `tools/decompress_stage0_data.py` reproduces it. The callback table at RAM `0x20000758` points to `0x4ce02`. That callback checks hardware bit `0x200` through `0x40e9c`; a surrounding mode-4 path at `0x57c74` posts `0x902` with reason `1` when the bit is absent. The bit appears in USB/power handling, so this path is not yet evidence of the user's Bluetooth playback shutdown. The `PowerOffStatusTimer` created at `0x59a24` uses a 3,000-unit interval and posts event `0x905` from callback `0x57c28`; its full state transition still needs tracing.
- In 0.6.4.0, the power object at RAM `0x200000a8` has a substate byte at `+1`. `PowerOffStatusTimer` setup (`0x59a24`) can set it to `2`; the battery-level monitor `0x59328` posts power-off event `0x902`, reason `6`, when its level argument is zero for eight consecutive calls and this byte equals `2`. The charging-bypass loop `0x50d30` also posts reason `6` when substate is `1`, event bit `0x200` is absent, and its flag is set. Both are concrete candidates for a plugged-in shutdown, but neither has been tied to this unit's observed shutdown; the cutoff logic should not be disabled without proving the battery reading/status condition.
- Both power-off conditions also exist in the older 0600 image at `0x58e2c` and `0x50be0` with the same zero-level counter and event/reason values. Their presence in two releases makes them intentional firmware behavior, although it still does not show which one fires on the user's speaker.

## Next static/dynamic steps

1. Trace which subsystem sets RAM `0x200000e8 + 3` in 0.6.4.0 and what event bit `0x200` means before linking either power-off candidate to the observed shutdown.
2. Locate the condition that disables keys in service mode, or determine whether the main application is bypassed entirely. The live button test confirms the loss of Volume+/Volume−/Play behavior.
3. Locate the state-write point triggered by the Play+Bluetooth chord. In 0.6.4.0, mode-state transition `0x901` leads to USB-audio event `0x806`, but the chord recognizer is still unknown.
4. Trace why USB task event `0xa03` is or is not emitted in service mode, and why the live CDC endpoint produces no version-query reply.
5. The installed firmware is 0.6.4.0 and its official OTA image is available. The custom partition CRC and static receiver path are mapped; capture or derive the full JBL Portable/JBL ONE OTA handshake and verify the boot/recovery behavior before sending an edited image. [JBL says Go 4 updates moved to JBL ONE](https://support.jbl.com/gb/en/howto/portable-app-partybox-app-migration-to-jbl-one-app-mtbw9ikdhub-emea/000054613.html), while the old public `go4_ota.json` still serves 0.6.4.0.
6. Before attempting a firmware modification, establish an image backup and recovery path for this board revision.

As of 1 November 2026, [JBL lists 0.7.4.1](https://support.jbl.com/us/en/howto/go-4-software-update-release-notes-us/000043859.html) (30 October 2026) with only a generic performance note. The older public `go4_ota.json` still serves 0.6.4.0, and a guessed `Go4_ota_all0741.bin` URL returned HTTP 403. There is no 0.7.4.1 binary here to compare or use as a patch base.

The [APK-derived OpenJBL product catalog](https://github.com/NiceDayZc/openjbl) lists two Go 4 PIDs, `20e4` and `210a`, with different OTA manifest paths. This unit reported `20e4`; a binary or procedure for the other PID must not be assumed compatible. OpenJBL documents control protocol details but deliberately omits OTA implementation.

Reference: [community firmware archive](https://github.com/pembem22/jbl-firmware), [Go 4 teardown](https://www.52audio.com/archives/221424.html), [JBL's Go 4 firmware notes](https://support.jbl.com/us/en/howto/go-4-software-update-release-notes-us/000043859.html).
