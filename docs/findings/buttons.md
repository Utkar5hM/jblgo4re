# Buttons and volume events

_Migrated verbatim from RE_NOTES.md on 2026-11-02; tighten bullets when touched. Addresses are 0.6.4.0 unless marked 0600._

- Partition 1 has an event-name table at `0xc2130`. IDs include `0x17` = `VOL_UP`, `0x18` = `VOL_DOWN`, `0x22` = `PLAY`, `0x23` = `PAUSE`, `0x88` = `ENTER_DEMO_MODE`, and `0x2` = `POWEROFF`.

- Main event routing around `0x929fe` forwards the volume and demo-mode events into `0x8e864`. The event name suggests that service USB playback may be tied to a demo mode, but that relationship is not yet proven.

- The current 0.6.4.0 event route in main partition 1 sends `0x17`/`0x18` to `0x8e128`/`0x8deb4` (not the similarly named legacy functions `0x8fc24`/`0x8f9b8`). Both volume handlers suppress the action only when the shared state byte at object `+0xf6` is `2` **and** another object byte `+0xf4` is at least `3` (`0x8fa60` and `0x8fa74` accessors). Otherwise they update one of the available volume indices and send an existing internal control message (`0x7ef68` or `0x0b524`) for two routing cases. This is a concrete candidate gate to compare in USB mode, but static code does not show the live values or prove the physical key events reach this router there.

- The two gate bytes have concrete writers: object `0x20021b20 + 0xf6` is written by `0x907dc` (called from `0x90d10`) and by state setter `0x90850`; byte `+0xf4` is populated by `0x90894` from an opaque helper result. This supports making the control suppression conditional on the actual active mode rather than globally removing safety/connection checks. The next safe patch candidate, if runtime observation confirms these values in USB mode, is to make the volume handlers take their normal volume-update branch in that mode and then reuse the already-existing volume message path. Play/Pause follows separate active-player helpers and needs its own route; this does not yet solve it.

- The `0x7ef68` branch is now traced past its queue: it posts a 3-byte control record to queue object `0x20021c84` with event ID `0x11000a`. Queue callback `0xa98dc` maps property IDs `0x2b7d`, `0x2b7f`, `0x2b80`, `0x2b81`, `0x2b83`, and `0x2b77`–`0x2b7c` to local event IDs, including `VOL_UP` (`0x17`), `VOL_DOWN` (`0x18`), and Play (`0x22`), then invokes callbacks from a table at `0x0c2550`. The two volume callback entries (`0xaa2e0`/`0xaa410`) and Play callback (`0xaa36c`) write fields in the per-property object via `0x21b60`/`0x232a4`; this is a stored property path, not evidence of an EQ/DSP gain write. `0x0b524` separately publishes event `0x0d31` through the application event broker. Logs: `volume_control_queue_refs.log`, `volume_handler_tables.log`, `volume_callbacks.log`, `play_callback_table.log`, `play_pause_control_callbacks.log`, and `volume_lowlevel_control.log`.

- Partition 0 function `0x40acc` maps six one-bit key masks (`0x01, 0x02, 0x08, 0x10, 0x20, 0x40`) to `AT+HMDevKEY=05,03,02,04,01,00` text and passes them to `0x40a80`. This gives us a key-code map for tracing the button scanner, but the physical button identities are not yet assigned.

- In partition 0, the handler near `0x523e6` receives key message `0x1c00`. For single-key masks `0x02, 0x08, 0x10, 0x20, 0x40` with a zero second word it calls `0x40af4`; `0x4d6fc` can enqueue `0x1c00` through `0x4d6e8` when the key-report gate is enabled.

- The diagnostic key gate is RAM byte `0x200004e8`: parser commands `AT+HMDevKIN` and `AT+HMDevKOF` set it to 1 and 0 respectively. With the gate enabled, `0x4d6fc` queues key message `0x1c00`; the handler near `0x523e6` formats selected masks through `0x40af4` (`AT+HMDevKEY=05/03/02/04/01/00`). `0x40aa8` frames those strings and `0x5a298` sends them on CDC IN endpoint `0x83` when the CDC transport is initialized. This gives a plausible host-side button bridge without adding HID, if the physical key scanner emits those messages during USB audio mode.

- Stage-0 startup calls `0x53ac4`, which runs power initialization `0x57128` and then `0x4cd38`. The latter looks up the `button_dev` driver, registers `0x4d6fc` as a callback, and passes the static button definition at `0x5d200`. Thus the telemetry callback is installed during startup; whether its driver reports events in the live USB-audio state remains unresolved. The second registered callback is a return-only stub at `0x58c24`.

- A timed live capture sent `AT+HMDevKIN`, listened on CDC IN for 60 seconds, then sent `AT+HMDevKOF` to restore the RAM gate. The speaker returned no CDC data. The prior synchronized button capture also had no CDC output while the user pressed Volume+, Volume− and Play, so this telemetry route is not currently a working bridge in service mode. The control scanner or event producer is likely inactive there; the gate itself is not enough.

- `AT+HMDevKIN` and `AT+HMDevKOF` in parser `0x4d71c` write the same state byte at RAM `0x200004e8` read by key-reporting gate `0x52610` via `0x4d6fc`. The address is present as a literal at `0x4dba4` and `0x52618`; the decompressed RAM image initializes the byte to zero. The two additional functions invoked by those commands (`0x418b6`, `0x419f0`) are stubs in this build. This gate controls diagnostic `AT+HMDevKEY` forwarding; it does **not** establish the cause of the disabled Volume+/Volume−/Play actions.

- Event callback `0x523e8` handles `0x900` by reading the mode byte via `0x5269c`; when it is `1` or `2`, it posts `0xa03`. Callback `0x51b60` handles `0xa03` by creating the `App USB Transmit` task whose entry is `0x44044`. These callbacks occur in the firmware's registration table at `0x5e18c` and `0x5e120`, respectively. The live service-mode CDC endpoint has not replied, so this static path does not establish that the task runs on the tested unit. The same `0x523e8` callback forwards eligible `0x1c00` key events to `0x40af4` for diagnostic reporting.

- Button transport correction: `0x4cd38` registers the button device's key callback at `0x4d6fc` plus its mode filter at `0x4d674`. The `0x4d6fc` callback forwards raw masks as event `0x1c00` only when RAM gate `0x200004e8` is nonzero; the registered event handler `0x523e8` converts recognized masks to `AT+HMDevKEY=xx` and frames them over CDC. Thus the firmware already contains a CDC control path; no HID interface is required for a host bridge. The live captures show no replies with the stock gate path, but do not establish whether KIN was accepted or whether the report task was active. A candidate now enables forwarding only when `0x4f4d2()` reports USB state 2. Actual key reports and button-to-code mapping still need live confirmation.

- Normal-mode button dispatch is now traced one level further in main partition 2. Event router `0x928c0` forwards `VOL_UP` (`0x17`) and `VOL_DOWN` (`0x18`) into `0x8cd2c`, which calls handlers `0x8e128` and `0x8deb4`. Those handlers update separate stored volume indices depending on active audio/peer state. In one branch they convert the index to 0..127 and submit a short message through `0x7ef68`; in another they convert to 0..255 and construct message `0xd031` through `0xb524`. Both use the generic callback/message layer at `0x1e7cc`, not a direct CoolFlux call. The destination worker and any later DSP-control hop remain unresolved, so this is not yet a safe USB patch point.

- The queue handler object used by `0xb524` is backed by RAM global `0x2002051c`. Its initialization at `0x9b88` creates a dispatcher object, registers callback `0x9e18` for event type `0x110e`, and records a callback context. `0x9e18` requeues selected event classes through the generic callback/message layer. This maps part of the internal application message framework, but does not show the final consumer for the volume payload. `tools/ghidra/FindLiteralXrefs.java` scans literal pools for RAM addresses and reports their code xrefs; it was added because the Ghidra project does not map the firmware's RAM region.

- The queue's worker is `0x6c050`; it uses `0x262f0` to resolve callback IDs from a table. The 13-entry table at `0xbc650` maps callback ID 10 to `0x9c50`. That callback treats the `0xd031` payload as event key `0x0d31` and republishes it to matching subscribers; it is an event-broker path, not a direct DSP write. The normal volume handlers also store a volume index in main-app object `0x200217a8 + 0x4b` through setter `0x5740`, which has no DSP call itself. The component that turns that stored index/event into an audible gain change remains unresolved.

- In the main-app event switch, Play (`0x22`) routes to `0x8daea` and Pause (`0x23`) to `0x8d9e0`. Those routines operate on active Bluetooth/player objects and invoke source-specific media helpers; when `FUN_00013f8c()` selects the alternate mode they update mode bits and post event `0xfc`. This maps normal Play/Pause handling but does not yet show a USB host-control path.

## Stage0 key pipeline (round 1, 2026-11-02, all `[stage0]`)
- `button_dev` = device record `0x200001f4` (ops `0x50abd`) in the RAM-init device table `0x20000200`. It is a GPIO-poll scanner, not IRQ or ADC. Config `0x5d200`: pin mask `0x7b`. `0x5d208`: polarity 1, debounce 3, timings 300/2000/5000/7500/10000. — [static]
- `0x50abc` stores the key table `{0x5d080, 19 entries, filter 0x4d675}`, creates timers (msgs `0x701`–`0x705`) and registers lookup `0x50a25`. Scan handler `0x459cd` handles msgs `0x700`–`0x707` (reads pins via `0x49520`). Gesture machine `0x457a8` → `0x45798` → `0x50a24(code,hi,type)`. — [static]
- `0x50a24` runs filter `0x4d675` (drops on ≤0), then callback `0x4d6fc` (consumes only when diag gate `0x200004e8` is set), else posts the event via `0x51ff8(evid,0,0)`. — [static]
- Key table: mask `0x01`→`0xe06` · `0x02`→`0xe04`/`0xe05` · `0x08`→`0xe00`/`0xe02`/`0xe03` · `0x10`→`0xe08` · **`0x20`→`0xf05`, `0x40`→`0xf06`** (types 4/1/2) · combos → `0xa05`, `0xa03`, `0x600`, `0xa00`, `0xa01`. — [static]
- Router `0x4f7c8`: `0xf05`→`0x4f510(0,2,0)`, `0xf06`→`0x4f510(0,3,0)` (ch `0x11` level step), so masks `0x20`/`0x40` are probably Vol+/Vol−. — [static] / [hyp] identity
- Filter `0x4d674(evid)`, in order: allow if `0x52664` (byte `0x2000012b` ∈ {1,2}); if PowerOffStatus `0x59a14`==2 allow only `0xa01`/`0x600`; drop if byte `0x2000018c`≠0; allow `0xe06`/`0xe07`; drop if `0x4f4d2()==1`; drop if `0x59a14==3`; drop if `0x55ad4(1)` (`0x20000285`)≠0; else allow. — [static]
- Scanner start: only `0x4cd8c` posts `0x700`, and only if byte `0x200010b8+9`≠0. That byte is set by `0x4d3e4` (from `0x566a4`) from a debounced read of GPIO mask 1 (`0x4d398`). No stop path was found. — [static]
- Why service mode is dead (unconfirmed): (1) the scanner never started; (2) the filter drops everything; (3) the main-ID path is not running. Live state of `0x200010b8+9`, `0x200000a8`, `*0x20000074` +0/+9/+0xd, `0x2000018c`, `0x20000285` and `0x2000012b` would settle it. — [hyp]
- Main has no `button_dev` (correction: stage0 and main are **not** alternate images; they run concurrently on two cores, see firmware-images.md). Its key gesture machine is `[main] 0x8cd2c`, fed by the HLP queue (`[main] 0x2c068` posts, `0x912b6` dispatches). `[main] 0x92d8c` maps flags `0x4000`/`0x8000` → `0x22`/`0x23`. The raw key source in main has not been found. — [static]

## Root cause: Vol± dead in service mode = scanner never starts (round 3, 2026-11-02, all `[stage0]`)
- **The break is scanner-start, not the filter.** Button init `0x4cd38` (run unconditionally at boot via `0x53ac4`; no byte0 gate) registers the key table + filter + diag callback, then posts scan-start msg `0x700` **only if `[0x200010b8+9] != 0`** (tail `0x4cd7a`: `ldrb r0,[r0,#9]; cmp r0,#0; beq 0x4cd94`). `0x4cd8c`/`0x51ff8(0x700,0)` is the sole `0x700` producer. — [static]
- **That gate byte = power key held at boot.** `[0x200010b8+9]` is written once (before the read) by `0x4d3e4` (`strb r0,[r1,#9]`, lit `0x4d3f0 -> 0x200010b8`) from boot init `0x566a4`. Its value = `FUN_0004d398()` = debounced read of GPIO port 1 pin 0 (`FUN_00052888(1,0,3,10)`). Normal power-on holds the key (byte≠0 → scanner starts). The Play+BT chord toggles `cfg[4]` and powers off; the byte0==2 reboot is self-initiated with no key held (byte=0 → `0x700` never posted → scanner never scans → no key events). This is why v1's whitelist was moot and the CDC diag route was silent. — [static]/[hyp] (byte=0 in service mode is inferred, not a live read)
- **Downstream is already mode-clean, so forcing scan-start suffices.** Scan handler `0x459cc` (`0x700`/`0x701`) and gesture `0x457a8`→`0x45798`→`0x50a24` have no byte0 check. `0x50a24` applies filter `0x4d674` (v1-whitelisted for `0xf0x` in byte0==2) to the evid, then posts `0x51ff8(evid,0,0)` (diag gate `0x200004e8`=0 here). State-2 pre-filter `0x529fc` (`0x5d238[2]`) passes `0xf05`/`0xf06` (fall through to `return 1`). Router `0x4f7c8` (`0x5e138`, enabled all modes) → `0x4f510(0,2|3,0)` ch-`0x11` step. Ch `0x11` (`0x20000514`, `0x56c50`) is live in service mode (stock USB-start sends `0x4f510(0,1,0x20)` on it). — [static]
- Ruled out as the break: (b) gesture/scan path byte0-gated — no; (c) `0x50a24`/`0x4f7c8` skipped in service mode — no; (d) level step ineffective — no (same channel the USB-start level-32 command uses). — [static]
- **Fix (`patches/usb-parity-v2`, built, not flashed):** v1's two edits + EDIT3 `0x4cd80 08 d0`→`00 bf` (NOP the gate branch) → `0x700` posted unconditionally. In-place, same-size, inner+outer CRCs recomputed; only stage0 changes (44 bytes). Residual risk: not mode-gated, so the scanner also starts on a charger-only boot of an off device (a `0x59a14()==2` guard won't fit the 2-byte slot without a code cave; the tail cave `0x5e3b8` was rejected as outside the inner CRC and before the unproven trailer, Q9). — [static]
