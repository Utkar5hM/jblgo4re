OTA partition ID 3 (`part2_unknown.bin` in the extractor) is not generic calibration data: its header contains `proj_bsp32.X`, `proj_bsp32.Y`, and `proj_bsp32.P`, plus `0kbsp32_go4.bin`. Embedded strings identify a DSP build dated May 15, 2025, with source names such as `BTAudioHandle.cpp`, `Interface.c`, and `data_path.c`. Its pipeline exposes paths named `player`, `recode`, `refer`, `lbren`, `lbrde`, `ldacen`, `ldacde`, `aacen`, and `aacde`; processing symbols include `hmProcess`, `VDSP_SetAlgParamInit`, `VDSP_SetAlgParamDyn`, and `setAdjustGain`. The `BSP32` label matches NXP's CoolFlux BSP32 core: a separate 32-bit DSP with X/Y data memories and P program memory. The partition is a wrapped image rather than ELF. Related CoolFlux literature describes 32-bit P words and instruction compaction/packing, but it does not establish the encoding used by this BSP32 build; the P-section format and code packing remain open questions. These strings do not prove which path USB or Bluetooth selects or whether `hmProcess` includes EQ.

The wrapper's three little-endian offset/size pairs are now mapped at header offsets `0x14/0x18` (X), `0x28/0x2c` (Y), and `0x3c/0x40` (P). For 0.6.4.0 they resolve to X=`0x400..0xf000`, Y=`0xf000..0x16c00`, and P=`0x20000..0x3f400`; the adjacent, non-overlapping ranges and section-name markers support this interpretation. The 0600 image uses the same X/Y ranges and P length `0x1ec00` instead of `0x1f400`. Y is byte-identical between these releases (SHA-256 `fccb8ecd...`), while X and P differ. `tools/extract_coolflux.py` validates the header, section markers, bounds, and non-overlap, then extracts each range and reports its hash. Example: `python3 tools/extract_coolflux.py captures/firmware0640/part2_unknown.bin --out-dir captures/coolflux0640`. The P payload is now isolated for targeted CoolFlux disassembly; its instruction encoding has not yet been decoded.

An ARM Cortex-M Ghidra import of this partition completed but discovered zero functions, as expected for a non-ARM image. NXP describes a dedicated C compiler, assembler, disassembler, linker, and ISS; its product page says the toolkit is provided via NXP and offers a 30-day evaluation by contact. A 2024 NXP support thread reports that no public CoolFlux compiler tools were available at that time. Sources: [NXP CoolFlux BSP32/toolkit](https://www.nxp.com/products/nxp-product-information/ip-block-licensing/coolflux-dsp-family:COOLFLUX-DSP-BSP), [NXP support thread](https://community.nxp.com/t5/MCX-Microcontrollers/MCXN947-Coolflux-BSP32-Use/td-p/1849864), [related CoolFlux DSP architecture paper](https://citeseerx.ist.psu.edu/document?doi=7f3379b43c6dad00a524c431f981c0959024b64f&repid=rep1&type=pdf). Next, reverse the wrapper's X/Y/P section offsets and determine the exact P-word representation before attempting to identify routines. Do not treat the zero-function ARM import as evidence that the DSP has no executable code.

- Channel 8 was a false lead for Bluetooth audio: its apparent “DSP” wrappers are used by `0x52f3c` to construct BLE GATT attributes (UUIDs `0x2800`, `0x2902`, `0x2a00`, `0x2a01`, and `0x2a05`), and by related discovery/attribute operations. Channel 8 is created at startup by `0x568e4`, with event callback `0x5695c`, and its handle is accessed through RAM object `0x200004f0`; the callback shape and wrapper command IDs alone do not identify an audio-processing route. USB PCM setup still uses the distinct channel `0x10` plus shared-memory/event-bit handoff. No evidence yet connects either channel to the DSP `player` path or EQ selection. Raw traces are in ignored `captures/ghidra/dsp_command_wrappers.log`, `dsp_channel_dispatch.log`, `dsp_command_callers.log`, and `dsp_channel_roles.log`.

- EQ correction: `0x43184` sends the stored profile through `0x4f588` using channel `0x0a`, not channel `0x11`. That channel is created by `0x56c80` and its handle is at RAM `0x20000518`. The sender builds type-4 payloads from config at `0x20000e60` and has Bluetooth/settings callers, but USB start does not call it. A post-USB call may cause the current profile to be applied to USB playback; this remains unverified because the DSP consumer and algorithm routing are unknown.

- Cloned the independent [OpenJBL project](https://github.com/NiceDayZc/openjbl) to ignored `captures/research/openjbl/` for its reverse-engineered JBL Portable APK protocol reference. Its model table lists Go 4 PID `0x20e4` as BLE with advanced level/preset EQ command `0x97` (and another Go 4 PID `0x210a` with the same route); its protocol document describes app-to-speaker EQ frames. This is useful for exercising the stock BLE EQ path and validating model-specific command payloads, but it does not provide USB/HID control or expose the speaker's internal DSP API. It cannot by itself bridge service-mode USB PCM to the normal Bluetooth processing chain.

- Main-app `0x780b8` is called during startup and sends a bank of one-byte settings using `0x7c11c` (transport helper `0x85ef4`, channel/group `1/0x34`), including indices `0x80`–`0x97`; the state bytes live near a device object at offsets `+0x34`–`+0x48`. The `0x97` index overlaps the JBL app EQ command number but is a separate internal transport namespace; no mapping from these settings to the CoolFlux `setAdjustGain` DSP call has been proven. Decompile output is in ignored `captures/ghidra/main_0640_eq_setter*.log` and `main_0640_dsp_command.log`.

- In the main image, startup at `0x76028` creates `App Task DSP` with entry pointer `0x2199` (Thumb entry `0x2198`). That task creates a 0x28-byte message queue, waits on it, then invokes a callback stored in each received message. A separate `App work_msg` task at `0xafbb4` also runs a callback dispatcher. This narrows the audio handoff search to queue/message producers; neither queue has yet been connected to the stage-0 USB PCM buffer or the Bluetooth audio route.

- The DSP task queue handle is stored at RAM `0x200217e0`; the queue-post helper `0xb0ef8` allocates and posts 20-byte callback records to it. Its wrappers are called by profile/control handlers around `0x7d040`, `0x7d2e8`, and `0x7d400`. These messages establish an app-task control/event channel, not a PCM path; the audio sample route remains to be found.
