# OTA container, CRC, receive path

_Migrated verbatim from RE_NOTES.md on 2026-11-02; tighten bullets when touched. Addresses are 0.6.4.0 unless marked 0600._

Container SHA-256: `2f440402006a65d29778075021e58cb174cf20626920187acfe0faaee75a5d19`. The file begins with `HMHEADER9`, has four `PARTHMDT` partitions, and ends with `FOOTERHM`.

The byte at header offset `0x10` is the partition count (`4`). Four 13-byte descriptors follow at `0x11`; each parses as a one-byte partition ID and three little-endian 32-bit fields: length, a still-unknown parameter, and a **custom CRC-32** of the partition payload. IDs are `1, 2, 3, 6`. Stage-0 function `0x43d4e` initializes the CRC to `0xffffffff`, feeds data through table function `0x44568`, and complements the result. The table at `0x5dc14` is a reflected CRC with polynomial `0x681bb522`. All four descriptor values match the computed CRC in both 0600 and 0.6.4.0, including the identical CRCs of three substantially different partitions. Standard zlib CRC-32 uses another polynomial and therefore does not match. `tools/extract_fw.py` now validates all four CRCs as well as markers and footer.

`tools/repack_fw.py` replaces one partition with data of the same length, updates its CRC in the header, and verifies the resulting container. Replacing stage 0 with identical bytes reproduced the official 0.6.4.0 OTA byte for byte (SHA-256 `56867f41...`); a one-byte test edit generated a new CRC and passed offline extraction. These checks establish the outer container format only. The device's board checks, flash mapping, boot behavior, and recovery path remain to be verified before a modified image is sent.

The same BLE command dispatcher that answered the live version query handles OTA-related opcodes. In stage 0, `0x57dcc` routes `0x43` to transfer setup `0x519f8` and `0x44` to a queued data path; `0x47`, `0x48`, `0x4a`, `0x4d`, and `0x4e` handle additional control/status operations. The setup path requires a 12-byte payload and checks the device mode through `0x4f4d2` before starting. Queued chunks reach `0x59494`, which checks sequence numbers and passes bytes to container parser `0x52dc4`. That parser recognizes `HMHEADER`, `PARTHMDT`, and `FOOTERHM`, and calls flash callback `0x5bc24`. The callback writes through `0x52460`/`0x53b50`; completion uses `0x41470` to compare a custom CRC of the written flash contents with the descriptor value. This is a static map, not a validated host-side update sequence. No update command was sent to the live speaker.

## Flash banking and commit (round 1, 2026-11-02)
- OTA IDs 1/2/3 map to A/B slots {0,1,2} or {4,5,6}. ID 6 is fixed slot 3. IDs 10/0x11/0x12 map to slots 9/7/8. — `[stage0] 0x4132c`, `0x41388` (slot table `0x200007a4+0x40+slot*0x20`) — [static]
- Bank selector is at flash `0x3000`: magic `0x5aa5`, flag byte `+3`, u16 counters `+4`/`+6`, CRC16 `+8`. The writer targets the bank with the lower counter. — `[stage0] 0x43c3c` — [static]
- Apply (opcode `0x4d`) → `0x597a0`: slots get status 3, user data is copied (`0x53ed4`), then `0x40fb8` bumps the lower counter to higher+1, sets `+3=1`, rewrites `0x3000` (single copy), and resets via `0x4a154(1)`. — [static]
- In-progress status 7 is written by `0x41138` to a record at flash `0x3ff100`. Nothing in stage0 or main reads status or clears `+3`, so the consumer is probably the mask ROM (`0x400000`). — [static] writer / [hyp] consumer
- The descriptor's "unknown parameter" is a per-partition version stored at slot `+0x48` by `0x414b0` (e.g. `0x00040600` = 0.6.4.0). No downgrade check was found. — [static]
- Per-partition CRC32 is checked only at OTA completion (`0x41470`). The slot table is then rewritten to sectors `0x0000` and `0x1000` (redundant). No boot-time image CRC exists in either image. — [static]
- **A main-only container would flip to a bank holding stale or blank stage0/DSP, so always send all 4 partitions.** — [static]+[hyp]
- The OTA control path (0xAA-framed `0x57774` → `0x57dcc`) lives only in stage0. Setup `0x519f8` needs `0x4f4d2()` ∈ {2,3}. — [static]
- No watchdog kick pattern was found. Software reset is `0x4a154` (register at `*0x45e0c`). Deliberate infinite hangs: `0x4f614`, `0x4f64c`, `0x49490`. — [static]

## In-partition integrity fields (2026-11-02)
- Each ARM partition ends with a 28-byte metadata block right before its `0xff` padding. stage0 `[stage0] 0x5e39c`: `u32 code_len=0x1e39c`, **`u32 go4crc(0x40000..0x5e39b)=0xf798464c`** (verified), then `00 06 03 03`…, build date `19 07 11 0a 04 2d` (2025-07-17 10:04:45), and `2e 00`. Main has the same layout at `[main] 0xd50cc` (date 2025-07-16 20:32:41). **Any code patch must recompute this CRC.** No reader exists in stage0 or main; the mask ROM is the suspected checker. — [static]
- Every partition (including part2 and part3) also ends with a 4-byte trailer (stage0 `c7 84 9e d1`, main `4b 05 00 32`). It doesn't match go4, IEEE or CRC32C (any reflect/init/xorout), adler32, a byte sum, md5/sha1/sha256 prefixes, or a forcing word to a constant residue over any sensible range. **Unidentified; keep it byte-identical.** — [static, negative]
- go4crc over the whole partition including the trailer = the OTA descriptor CRC (the known outer check). — [static]
- part3 (ID 6, 32 KiB) is high-entropy up to the last byte. It might be keys/signature or encrypted data. Unknown. — [hyp]

## Recovery / brick-risk verdict (Q5, 2026-11-02)
- **The entire OTA receiver is stage0-only.** Dispatcher `0x57dcc` (sole caller `0x57774`, the 0xAA frame parser, whose sole caller is event handler `0x4e4d0` on event `0x1604`), setup `0x519f8`, data `0x59494`, apply `0x597a0`, flash helpers `0x43c3c/0x43dd0/0x40fb8/0x41388/0x4149c`. `[main]` has no `0x3000` selector access, no OTA strings, no `0x5aa5`. **So a stage0 that fails to boot cannot receive a replacement OTA — a bad stage0 is a potential brick.** — [static]
- **BLE OTA works in normal mode, not service mode.** `0x4e4d0` returns early when byte0==2, dropping event `0x1604` before it reaches the dispatcher; service mode also skips the GATT table build (`0x57128` calls `0x52ff4`→`0x52f3c` only when byte0!=2; that builds GAP/GATT `0x1800/0x1801`, `0x2a05`, custom chars w/ CCCD). Normal mode builds it and doesn't gate the event. — [static]
- **OTA needs main ready.** `0x519f8` has no mode check but gates on `0x4f4d2()` ∈ {2,3}. `0x4f4d2` ignores byte0; it needs glob bits[5:4]==1 (set once at main init `[main] 0xb2120`→`0x805b4(1)`, stays 1) AND `runs+0` (written by `[main] 0x2c644`, read `0x2c488`; value 3 = connected per `0x2c980` events `0x122/0x123`) in a BT-link state. **A bricked main likely drops `0x4f4d2` to 0 and blocks OTA too.** So a bad main is recoverable only if it still reaches a BT-ready state. — [static]/[hyp]
- **Flag byte +3 is write-only** (set=1 at `0x40fb8`, never read/cleared in either image; selector reader `0x43c3c` reads magic/+8 CRC16/+4 counter only, `0x41388` reads +4/+6). No boot-attempt/retry counter exists either. If the ROM does trial-boot rollback it would key off +3, but that is unprovable here. — [static]/[hyp]
- **No watchdog.** `0x4a154` writes SCB AIRCR (`0xe000ed0c` = `0x05fa0004`, SYSRESETREQ) — a plain software reset. No periodic kick / WDT arm in either image. — [static]
- **Commit is non-atomic, no post-apply re-verify.** `0x40fb8` bumps the counter, sets +3, recomputes the CRC16, then `0x43dd0` **erases the whole `0x3000` sector then writes 10 bytes** — single copy, so power loss mid-window leaves the magic invalid. The per-partition CRC check runs earlier in `0x53b50`/`0x41470` (reports status 4 to host on mismatch); apply `0x597a0` calls `0x40fb8` **unconditionally even after a CRC failure**. The table at flash 0x0 is likewise erased-then-written with no backup (`0x4149c`). — [static]
- **ROM-dependent (unprovable from these two images, mask ROM at `0x400000`):** how the ROM picks a bank (counters only, or image validity / +3), whether it rolls back on a failed boot, and whether it exposes a UART/USB download mode. Web search found no Zgmicro-specific ROM recovery docs (SoC = Zgmicro BLE-audio, `ZGMICRO`/`zgbledv`/`ZGMC_MasterExit`/`VSDK_` + 3DSP CoolFlux BSP32). Many BT/MTK/i.MX ROMs enter a download mode when the boot image fails verification, but this cannot be assumed for Zgmicro. — [static]+[hyp]
- **Bottom line:** every code change to the goal requires a stage0 edit (the EQ sender `0x43184` lives in stage0), and flashing stage0 carries a real, unquantified brick risk with no proven recovery channel. **Do not flash until recovery is proven** (datasheet, a sacrificial second unit, or a confirmed ROM download mode). v1/v2 are kept build-verified and ready for that day. — lead

## Q6 host-side OTA wire protocol (2026-11-02) — blind spot resolved, static
- **Transport:** GATT write char `…0002`, notify char `…0001` (same as `ble_probe.py`). Frame = `AA <op> <len> <payload>`. `len` is 1 byte for most opcodes, **2 bytes big-endian for `0x44` (data)** and for `0x97/0x98/0x99`. Parser `[stage0] 0x57774` scans for the `0xAA` sync, then dispatches via `0x57dcc`. — [static]
- **Blind spot broken.** The `0x53xxx` helpers were unreadable only because the index/`gh.sh` run `-noanalysis`; forcing `disassemble`+`createFunction` (DumpFunctions.java) and cross-checking the truncated ones with capstone recovers them. Resolved map (all `[stage0]`): `0x53df0` = set `ctx+0x64`; `0x53dd8` = get `ctx+0x64`; `0x53e94` = if arg≠2, compare stored id vs arg, on mismatch store it and return 2; `0x53e74` = **memset(dst,0,0x16)** (clears the 22-byte status struct — not a readback, confirmed by capstone at `0x53e74`); `0x53d38` = partition-table layout query (entries 0xd bytes, count at `tbl+4`); `0x53c58` = readiness/status char (cached at `*DAT_53cec`); `0x53b50` = **per-partition write+finalize+status-callback**; `0x53bc8` = apply-time per-partition commit (writes state 3 via `0x41138`). — [static]
- **`0x43` setup `[stage0] 0x519f8`** (payload len must be `0xc`=12): `[0:4]` BE u32 (→ `0x53df0`, stored at `ctx+0x64`, echoed/compared by `0x53e94`), `[4:8]` BE u32 → total-size counter (`obj+4`=remaining, `obj+0xc`=total), `[11]` flags (`hi nibble`→`DAT_51afc`, `lo nibble`→`0x53e94`). Gate: `0x4f4d2()∈{2,3}` (main ready) AND `0x53c58()==0` (0 = idle/ready), else error reply `0x0e`. — [static]
- **`0x44` data `[stage0] 0x59494`:** device holds a sequence counter at `*DAT_594f0`; an incoming frame whose seq == counter is written, counter++ and remaining-bytes decrement; last byte → success reply `0x00`; seq mismatch or zero len → error `0x11`. Writes land in the **inactive** bank via `0x41024` (erase-on-4K-boundary then program). — [static]
- **Per-partition CRC verify EXISTS and is reported to the host (corrects earlier "no CRC gate" framing).** On the last chunk of a partition (`0x53b50`, flag==1): `0x41470` calls `0x43d4e`, which **reads the just-written flash back in 0x100 blocks and accumulates the go4 CRC-32** (`0x44568`, same reflected poly `0x681bb522`, final `~`), then compares it to the expected CRC stored at the partition descriptor `+2`. Mismatch → `0x41470` returns `-7`; `0x53b50` reports **status 4** to the host via its completion callback (`(*(cbtbl+4))(status, obj)`). Write-fail → status 3, metadata-record-fail → status 5, success → status 0. `0x4149c` additionally re-CRCs all 10 descriptor records (`+0x1d4` vs computed, `0x44528`) and rejects with `0x461` on mismatch. **⇒ The device self-verifies every partition and tells the host; a corrupted transfer surfaces as status 3/4/5, not silence.** — [static, confirmed]
- **`0x4d` apply `[stage0] 0x597a0`: still commits UNCONDITIONALLY.** Runs `0x576c8`→`0x53ed4` (per-slot state scan) then `0x53bc8` (marks each partition state 3), builds the host reply with status (0 ok / `0xc` fail), and then **always** calls `0x40fb8` (bank flip, bump counter, set `+3`, rewrite selector) and `0x4a154(1)` (SYSRESETREQ) — there is **no `if(status==0)` guard** around the flip. The `0x57dcc` 0x4d branch pre-rejects only if the transfer is **incomplete** (`*(obj+4)!=0`) or `0x52604` state is wrong. — [static, confirmed]
- **Net safety model (this is the usable conclusion):** the brick-by-corruption vector is fully host-controllable. Stream all 4 partitions; after each partition's final chunk, read the completion notification and require **status 0**; abort (never send `0x4d`) on status 3/4/5. The device's own readback-CRC is the verify — it does not have to be reconstructed; it only has to be *observed* in the status frame. The residual, protocol-independent risk is a partition that is CRC-valid but behaviorally wrong (a bad stage0 that boots incorrectly) = the Q5 mask-ROM-rollback unknown, unchanged by any of this. — [static]/[hyp]
- **A transfer without `0x4d`** writes only the inactive bank and is reversible (active bank + boot untouched; no auto-apply found). A dry-run sender (setup+data, read status, **never** `0x4d`) is safe and empirically validates the whole protocol on-device including the real per-partition CRC result. — [static]
- **Recommendation (updated):** a from-scratch sender is now viable because the status path is readable and self-verifying. Still prefer capturing one official OTA (BLE HCI snoop) to confirm exact chunk size, the `[0:4]` id/sequence convention and `[11]` nibble meaning before any commit — cheap insurance, and it reveals abort/recovery behavior. Build/verify the sender offline; `0x4d` is the user's call on present hardware, after a dry-run shows all-status-0. — lead

## Q6 CLOSED — host protocol confirmed from JBL Portable APK (2026-11-02)
Ground truth from **JBL Portable 6.9.33** (`com.harman.ble.jbllink`, pkg under gitignored `captures/apk/`), classes `com.harman.sdk.command.*`, `com.harman.sdk.impl.ota.UpgradeFirmwareFileUtils`, `com.harman.sdk.utils.DfuCRC`. The Go 4 is a **Vimicro/Actions** product (`DeviceUtils.isVimicroOrActionsProduct`), BLE GATT transport. This confirms and completes the static RE above. — [static, APK]

- **Frame:** `AA <cmd> <len> <payload>`. `len` = 1 byte for all opcodes **except `0x44`/`0x97`/`0x98`/`0x99` = 2 bytes big-endian** (matches parser `0x57774`). Same GATT write `…0002` / notify `…0001` chars as `ble_probe.py`. No id byte before `cmd`. — [static, APK]
- **Opcode map (host→device, response):**
  - `0x4a` ReqDfuVer → resp `0x4b` (device's current DFU version string).
  - `0x43` ReqDfuStart (payload 12B, below) → resp `0x00` then `0x45` (TRANSFER_BEGGING).
  - `0x44` SetDfuData (payload = `[pkgIndex&0xff] + chunk`) → resp `0x45` (TRANSFER_NEXT) per chunk.
  - `0x45` NotifySectStart (section/next marker).
  - `0x47` NotifyDfuCancel (abort; payload `[1]`).
  - `0x4d` ReqTriggerUpgrade (payload empty) → resp `0x4c` (TRANSFER_COMPLETED), then device flips bank + resets.
- **`0x43` setup payload (12B, Vimicro byte order), built by `ReqDfuStartCommand.initPayload`:**
  - `[0:4]` = `fwFileCrc` as `int2ByteArray` (big-endian) then **16-bit word-swapped**: `[c8,c0,c24,c16]`.
  - `[4:8]` = `fwFileLen` big-endian (plain).
  - `[8:11]` = 3-byte config/version (`DeviceUtils.getConfigVersion`, `major,minor,patch`).
  - `[11]` = flag: `1` if file version **equals** device's current DFU version, else `2`.
- **`fwFileCrc` / `fwFileLen` = whole-container** (`DfuCRC.fileCrc` over the entire HMHEADER9 `.bin`; len = file length). The host streams the container **linearly**; the device parses HMHEADER9 and writes/verifies each partition internally. So the setup CRC is a *different* algorithm from the per-partition go4 CRC. — [static, APK]
- **Setup/whole-file CRC algorithm (`DfuCRC`, Vimicro path):** MSB-first table CRC — `crc = ((crc<<8) ^ TABLE[(crc>>24)&0xff] ^ byte) & 0xffffffff`, **init 0**, input = `data || 0xFF*4` (4 trailing `0xFF`), **no final XOR**. Reflected poly recovered = non-standard; the 256-entry `revCrcTable` is captured verbatim. Implemented in **`tools/setup_crc.py`** (pure calculator). Stock `Go4_ota_all0640.bin` → `fwFileCrc 0x28c5d390`; usb-parity-v1 → `0xf3f11828` (len `0x15106d` both). — [static, APK]
- **Chunk size = negotiated ATT MTU − 7** (BLE GATT, Vimicro). Each `0x44` payload = `[pkgIndex] + up to (MTU-7) data bytes`; `pkgIndex` increments per chunk (`&0xff` wrap) and the device's seq counter (`*DAT_594f0`) must match it. — [static, APK]
- **Flow (`UpgradeFirmwareFileUtils`):** `requestDFUInfo`(0x4a) → `doReqDfuStart`(0x43) → on `0x45` `sendNextPacket` loops `0x44` until the whole file is sent (`onTransferCompleted`) → `triggerUpgrade`(0x4d). **Any failed command mid-transfer → `onTransferError` → abort; `0x4d` is never reached.** On `0x4c` the app reads reply `payload[0]` and calls `onApplyNewFirmware(device, payload[0])` (the device's apply-result byte). — [static, APK]
- **Safety (confirmed both sides):** the official app only sends `0x4d` after a clean full transfer; the device CRC-checks each partition during the data phase and signals failure (status 3/4/5) which the app treats as a transfer error and aborts. A sender that mirrors this — stream, require success acks, withhold `0x4d` on any error — cannot brick by corruption. Residual risk = CRC-valid-but-bad stage0 (Q5). — [static, APK]
- **Sender:** `tools/ota_sender.py` — offline **planner by default** (no BLE); a transmit mode streams setup+data over BLE and reads acks but is structurally incapable of emitting `0x4d`; a separate commit mode (interactive-confirmed, user-present) is the only path that sends `0x4d`, and only after every chunk acked. `guard.sh` blocks the lead from running it; the user runs it with `!`.

## Q6 LIVE on-device test (2026-11-02) — transmit works, data-accept is the open blocker
First real BLE runs against the user's Go 4 (guard.sh removed at the user's request). — [live]
- **Transport + control confirmed live.** Connect, notify, and control opcodes all work: `0x4a`→`aa4b03 000604` (device DFU ver 0.6.4), `0x43` setup (`aa430c 1828f3f1 0015106d 000604 01`)→`aa00024300` then **BEGGING `aa4506 01 00000000 00`** (status 1, breakpoint offset 0), `0x47`→`aa00024700`. So setup is accepted and the device enters receive-from-offset-0. — [live]
- **Data write mode: must be write-without-response.** The control char (`…0002`) has props `['write-without-response','write']` and does **not** ATT-ack data writes. Write-WITH-response blocks ~5000 ms per packet (BlueZ waiting for a response that never comes) → the device's OTA session times out ~packet 10 and emits status `0x04`, then goes silent. Write-WITHOUT-response = ~1 ms/write. `ota_sender.py` now uses `response=False` for `0x44`. — [live]
- **Open blocker: the device commits ZERO data blocks.** For every `0x44` packet (any size 14–240 B, any write mode), the device only emits a ~5 s heartbeat `aa4502 02 ff`. Decoded: `0x57290(_,2,idx)` builds `aa45 02 <idx>` with `idx = (*DAT_583dc / *DAT_583d4 − 1)&0xff`; `0xff` ⇒ committed-block counter `DAT_583dc == 0` ⇒ **nothing accepted**. The JBL app itself treats `aa450202ff` as noise (literal log string "received incorrect aa450202ff, ignored this event"); over BLE the app is notification-driven (its windowed burst in `onCharacteristicWrite` is BR/EDR-only). — [live]/[static]
- **Contradiction with static:** the clean accept path `0x43fdc`→`0x59494(chan, data=payload+2, seq=payload[1], len)` checks `expected_seq(*DAT_594f0)==seq` (expected=0 after setup) and `len!=0`; my first packet is pkgIndex 0, len≠0, so by the code it *should* be accepted and increment. It is not. A runtime detail (dispatcher gate `*DAT_583dc & 0xff == payload[0]`, a required channel/param, or a prior command) differs from the reconstruction and the merged decompile won't resolve it cleanly. — [live]/[hyp]
- **No brick risk incurred:** device committed nothing, `0x4d` never sent, inactive bank not meaningfully written; `0x4d` apply is also gated device-side on `remaining==0` so a partial transfer cannot be applied. — [static]/[live]

## Q6 FLASHED SUCCESSFULLY — usb-parity-v1 applied to the device (2026-11-02)
usb-parity-v1 was streamed and applied to the user's Go 4 over BLE; the device rebooted healthy. — [live]
- **What made it work (vs the earlier stall):**
  1. **Correct LE address.** The Go 4's BLE address (`55:F2:60:8B:8D:FB`) differs from its classic BR/EDR MAC (`90:F2:60:8B:8D:FB`). Scan/connect by the LE address (or by Harman mfg `0057` / name), not the classic MAC. While classic-audio-connected it suppresses its LE advert, so remove the host pairing / disconnect audio first.
  2. **Write-without-response for `0x44`.** The control char doesn't ATT-ack data; with-response blocks ~5 s/pkt and times the session out.
  3. **Stream, don't wait per packet.** Accepted packets are answered with SILENCE; only a mismatch yields `02 ff` and only every ~Nth accept yields `02 <idx>`. Fire packets at a steady pace (~8 ms) and only abort on an explicit error frame.
  4. **Clean counter.** The accept gate `0x58036` wants `pkgIndex == (counter & 0xff)`; a power-cycle gave a clean start and the sequential `pkgIndex 0,1,2,…` matched (zero `02 ff` the whole run = all accepted).
- **Apply:** `0x4d` delivered; `write_gatt_char(response=True)` hangs because the device resets before ATT-responding (cosmetic — the PDU is delivered first; TODO: send `0x4d` write-without-response). Device flipped bank and rebooted.
- **Post-flash health (read-only probe):** `aa4100`→`aa42 04 00060400` = fw **0.6.4.0**; PID `0x20e4`; battery 100%/charging; control service fully responsive; LE adv now exposes the full GATT set. **Not bricked.** — [live]
- **Open:** behavioral verification of the patch (EQ + Vol± in the Play+BT USB service mode) is a physical user test; firmware version is unchanged (v1 keeps 0.6.4.0) so it can't be read over BLE. — [live]/[pending]
